可以整理成下面这段，适合放到博客/调试记录里：

i.MX6ULL 外部模块编译环境复盘 一开始我在 Docker Ubuntu 20.04 里直接使用系统自带的 arm-linux-gnueabihf 交叉编译链，也就是 GCC 9 版本。结果编译厂家旧内核时不断出问题，甚至 zImage 都无法正常生成。 后来查看开发板当前系统的 /proc/version，发现板子原始内核是用 GCC 4.9 编译的。于是改用厂家/官方推荐的 arm-linux-gnueabihf GCC 4.9 工具链。 切换工具链后，交叉编译器问题基本解决，但 menuconfig 又因为宿主环境依赖问题跑不起来。由于本次目标只是复现厂家内核配置并编译外部模块，不需要真正进入图形配置界面，所以没有继续折腾 menuconfig，而是直接沿用/修改 .config。 之后又遇到老内核源码在新宿主 GCC 下的兼容问题，例如 yylloc 多重定义。这类问题本质上是老代码默认依赖 GCC 早期的 -fcommon 行为，而新 GCC 默认变成了 -fno-common。最终在编译内核时加入： make HOSTCFLAGS="-fcommon" zImage modules dtbs 绕过宿主工具编译阶段的问题。 最后，内核成功编译，出现： zImage is ready 同时 Module.symvers 里也生成了 module_layout，外部 hello.ko 模块重新编译后可以正常 insmod 加载。

可以再提炼成一版“踩坑结论”：

结论：

  1. 老 BSP 不要随便用新 GCC。 i.MX6ULL 这类旧内核工程，优先使用厂家推荐的交叉编译器版本。
  2. cat /proc/version 很重要。 它可以直接看到当前板子内核当初是用哪个 GCC 编译的。
  3. CROSS_COMPILE 和 HOSTCC 是两套东西。 arm-linux-gnueabihf-gcc 编 ARM 内核代码； 宿主机 gcc 编 scripts/dtc、menuconfig、modpost 等构建工具。
  4. menuconfig 不是必须步骤。 如果只是复现已有配置，可以直接使用厂家 defconfig 或现成 .config。
  5. 老内核遇到 yylloc 多重定义，可以考虑 HOSTCFLAGS="-fcommon" 或修改 scripts/dtc。
  6. 外部模块能不能加载，不只看 hello.ko 是否生成。 还要看 vermagic、Module.symvers、module_layout、CONFIG_MODVERSIONS 是否对齐。

更像你自己的口吻可以写成：

这次最离谱的点是：我本来只是想编一个 hello.ko，结果真正折磨人的不是驱动代码，而是复现厂家当年的内核编译环境。 Docker Ubuntu 20.04 自带的 arm-linux-gnueabihf-gcc 是 GCC 9，但板子当前内核是 GCC 4.9 编出来的。新 GCC 编老 BSP 会出现各种奇怪问题，zImage 都出不来。 最后改成官方推荐的 GCC 4.9 工具链，避开 menuconfig，直接使用配置文件，并在编译时加 HOSTCFLAGS="-fcommon"，才让老内核顺利编过，最终看到 zImage is ready。 这次最大的教训是：嵌入式 Linux 不是有源码就能编，必须先对齐板子当前内核、厂家配置、交叉编译器版本和构建环境。
