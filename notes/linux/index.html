再战Linux驱动

编译环境搭建

摘要 如果你很随意的选择内核和工具链，等待你的是无尽的折磨。我就是那一个。我本来只是想编一个 hello.ko，结果真正折磨人的不是驱动代码，而是复现厂家当年的内核编译环境。 Docker Ubuntu 20.04 自带的 arm-linux-gnueabihf-gcc 是 GCC 9，但板子当前内核是 GCC 4.9 编出来的。新 GCC 编老 BSP 会出现各种奇怪问题，zImage 都出不来。 最后改成官方推荐的 GCC 4.9 工具链，我去了下载的地方，一看，WTF，没有Mac平台，赶紧回到PC虚拟机，下了x86_64平台的，避开 menuconfig，直接使用配置文件，并在编译时加 HOSTCFLAGS="-fcommon"，才让老内核顺利编过，最终看到 zImage is ready。 我是如何折腾环境的 mac用着很爽啊，既然mac能编stm32裸机程序，那linux的驱动应该也可以吧，然后我分析了一下，发现mac不是原生linux，可能会出很多问题，改用了Docker上轻量Ubuntu20.04。 然后刚开始不知道内核要先编译一遍生成zImage，然后我直接用内核编译了hello.ko,编译失败，说缺少module.symvers. 我用deconfig编译了一下生成.config。然后执行了.sh脚本。我不知道怎么样是编译成功，看起来没有报错，然后我就编译了hello.ko，这次成了。赶紧scp -O到板子上，然后insmod，Fuck，没有layout。然后折磨开始了，我还没意识到问题。来回折腾老半天，在内核里一顿编译，就是缺少layout。最后我被折磨够了，赶紧看了官方的资料，4.9的版本，看了下载的包，找mac，WTF，No way！没有Mac平台。我赶紧把Mac丢进了垃圾桶🤣。 打开PC linux虚拟机，下载4.9 x86_64的版本，啊，编译内核，过了几秒钟，一个error。找不到依赖，编译不过menuconfig，图形界面配置干脆不要了，注释掉，再编译一下，在看yylloc重定义，🤔，求救一番之后，加了HOSTCFLAGS="-fcommon"，终于舒服啦，zImage is ready。编译hello.ko，然后scp -O，insmod，搞定。 驱动学习日后感悟 原来我以为Linux驱动学习需要一个开发版，但是，实际上不需要，只需要一个Linux环境，Docker不行，因为Docker的内核是定制的，和generic的内核版本不一样，驱动编译好不能直接验证，最终还是需要Linux虚拟机。所以Mac不是不能做驱动开发，只是老工具链的问题，工具链实际上就是特定平台的ELF文件。 总结 Linux驱动编译的前提 拥有板子对应的原厂或者厂商的内核(imx6ull 4.1.15) 拥有同版本的编译工具链(arm-linux-gnueabihf-gcc 4.9) 进入内核目录执行脚本(或者自己编译zImage) 要看到zImage is ready。 Linux驱动编译以及测试 然后用这个内核去编译你的驱动程序 将驱动程序通过网络传到板子上 insmod 然后 rmmod。 Mac环境不适合老旧项目 在Mac上交叉编译Linux的内核会有哪些问题 老旧项目用的工具链没有Mac平台，有x86_64. Docker Ubuntu环境下, 工具链版本新，还是解决不了⬆️个问题。
