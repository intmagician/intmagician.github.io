Linux驱动开发｜现代Linux“Driver-Bus-Device”总架构

所有的Device在驱动模型里，都挂在总线上，没有例外。其中Platform属于其中一种，它是Platform Drivers - Platform Bus - Platform Devices。 Driver-Bus-Device模型 在/sys/bus/可以看到众多bus，这其中能看到常见的usb、spi、serial、platform、pci、i2c、gpio这些。 设备会事先挂载在某一种总线上，然后通过match compatible来将某类bus下driver与device匹配。匹配成功就会调用probe函数。 pci bus 下会有 pci_driver and pci_device. i2c bus 下会有 i2c_driver and i2c_device. platform bus 下会有 platform_driver and platform_device. Bus PCI Bus USB Bus I2C Bus SPI Bus Platform Bus Platform Bus 是一条虚拟总线。它是专门为一些设备准备的，这些设备不可热插拔，不能自动枚举。不能自动枚举的话就是，没有张嘴，只能靠别人找它，它不吭声，没有usb设备主动。目前是这么理解的。 像很多嵌入式外设：led、电机驱动芯片、adc、key等等。 官方公开文档点击👉Platform devices and drivers struct platform_driver { int (*probe)(struct platform_device *); void (*remove)(struct platform_device *); void (*shutdown)(struct platform_device *); int (*suspend)(struct platform_device *, pm_message_t state); int (*resume)(struct platform_device *); struct device_driver driver; const struct platform_device_id *id_table; bool prevent_deferred_probe; bool driver_managed_dma; }; 怎么注册Platform_driver 自己编写probe和remove函数然后通过of_device_id和platform_driver结构体来注册 ...

Linux驱动开发｜设备树学习笔记

如果你了解linux原始的驱动编写，你就会明白，设备树只是一个更优、更便捷的数据结构，如果把设备信息写成.c的结构体，那么每次修改都要编译内核，内核里边也有一堆.c文件，它们都是内核外围的，很臃肿。 所以在学设备树之前，一定要建立这样一个思想，我写设备树跟写C结构体描述设备是在做同一件事情，这样的话，你可能就不会很疑惑，比如：设备树是在干什么，设备树里一堆搞不清楚怎么来的名字是怎么回事，内核是怎么获取的这些东西，最终又是怎么成功驱动设备的。 简单来说dtb就是描述设备信息的文本，内核里边有个查找函数来查想要的信息，然后给驱动程序。就一个复杂版二叉树，dtb就是把二叉树遍历一遍，也就是flatten扁平化，然后给uboot和内核使用。 dts语法 node node有以下三种形式，带label的方便其他node引用，&label则是引用。类似C语言的变量名与取变量地址，还有一个特殊的根节点是/。 node_name { } label: node_name@address { } &label { } &label可以用来补充被引用的node property 除了node_name还有它的起始地址外，它还包含了很多属性，用来补充node信息。 compatible compatible = "manufacturer,model"; compatible = "arm,cortex-a7"; compatible = "fsl,imx6ull-gpmi-nand", "fsl,imx6ull-gpmi-nand"; compatible需要设备树跟驱动模块能够匹配。命名一般都有现成的。 device_type device_type = "cpu"; cells #address-cells = <> #size-cells = <> #interrupt-cells = <> cells的单位是32位，0指的是0x32位,1指的是1x32位,2指的是2x32位，这几个常用。 address-cells指的是地址是多少位的。 size-cells指的是最大需要用多少位数来表示，没大小就是0，1代表u32，2代表u64。 interrupt也一样。 reg reg = <address, size> 对应#address-cells和#size-cells的值。address是起始地址，size是大小。可以去手册的Memory Maps这个章节查看，一般reg配置看这里就行了。 ranges ranges = <child-bus-address parent-bus-address length> / <empty>; 对应#address-cells和#size-cells的值。 ranges用于总线地址映射，就是把子总线地址翻译到父总线地址，一个地址翻译表。子节点里的reg地址，不一定是cpu看到的物理地址，需要经过ranges翻译。 phandle phandle = <1>; phandle跟label的作用一样，label需要&label来引用，但phandle不行，它必须是独一无二的，不能跟别的一样，应用的时候需要引用对应数字。 interrupt-parent = <1>; Linux驱动开发｜编译环境搭建

我是如何折腾环境的 在两轮自平衡车项目里，用mac搭建了裸机开发交叉编译环境，通过stm32flash进行串口烧录和调试，直到小车电池没电了，充电器又找不到，就先放下，学Linux驱动。 既然mac能编stm32裸机程序，那linux的驱动应该也可以，mac不是原生linux，可能会出很多关于依赖的问题，所以，改用Docker上轻量Ubuntu20.04。 一如既往，先瞎折腾，踩一遍坑。 找到板子的内核，然后用docker写了最基本的hello.c，然后编译，报错，编译失败，缺少module.symvers。(这里是因为内核没有编译通过，没有编译defconfig，还有zImage) 依然是不看官网教程pdf，然后瞎搞。 我用defconfig编译了一下生成.config。然后执行了.sh脚本。编译成功没成功也不知道，然后编译了hello.c，生成了hello.ko。 通过scp -O到板子上，然后insmod，失败，没有layout信息。(这里是因为内核没有编译通过，docker下的交叉编译工具链版本高，工具链不适配) 知道内核没编译过，就折腾了好几轮，1～2小时，受不了了。看官方教程，看了工具链版本与下载地址。没有Mac版本，不搞Mac了，这个临时搞不来。 打开PC linux虚拟机，下载4.9 x86_64的版本。 编译内核，过了几秒钟，一个错误，找不到依赖，编译不过menuconfig，图形界面配置注释掉，再编译一下，在看yylloc重定义，查了资料后，加了HOSTCFLAGS="-fcommon"，终于舒服啦，zImage is ready。编译hello.ko，然后scp -O，insmod，搞定。 Linux驱动编译的前提 拥有板子对应的原厂或者厂商的内核(imx6ull 4.1.15) 拥有同版本的编译工具链(arm-linux-gnueabihf-gcc 4.9) 进入内核目录执行脚本(或者自己编译zImage) 要看到zImage is ready。 Linux驱动编译以及测试 然后用这个内核去编译你的驱动程序 将驱动程序通过网络传到板子上 insmod 然后 rmmod。 Mac环境不适合老旧项目 在Mac上交叉编译Linux的内核会有哪些问题 老旧项目用的工具链没有Mac平台，有x86_64.
